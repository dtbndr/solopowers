# "Cannot Verify From Diff" Items

Part of `solopowers:workstream-driven-development`.

The reviewer may report `⚠️ Cannot verify` for requirements hidden by the diff or missing Test Evidence. This is uncertainty, not a verdict or finding severity. Inspect whether existing evidence or direct repository inspection establishes the affected contract. If evidence is missing or inadequate, correct it and redispatch review of the same recorded range (an unrecoverable historical RED instead follows the ladder below, without redispatch); if direct inspection resolves the uncertainty, record the evidence and outcome. A confirmed contract gap enters the fix loop. The status alone is neither a correction request nor proof of a defect. For evidence omissions, inspect the report and worktree; ask the implementer to amend `report.md` without a commit when checks ran but were not recorded. If required checks can be run at the reviewed tip without code changes, run them and record the evidence; do not enter a fix round for evidence-only work. If missing coverage requires code changes, enter the normal fix loop; never fabricate historical RED. If the evidence cannot be established, follow the unrecoverable-RED ladder below (for RED, rung 3 logs a gap rather than escalating).

## Unrecoverable historical RED

Applies when the worker reports a pre-implementation RED but its raw output or edit sequence is no longer recoverable (tests and implementation committed together, report lost or truncated), or when a fix landed without any RED. For the latter, rung 1 does not apply: rung 2 (reconstructed RED, labeled as fresh evidence) is the workstream's standard in place of discard-and-redo, and otherwise rung 3 logs the gap and work proceeds. For a fix round, rung 2 restores the fix's implementation files from that round's `FIX_BASE` (and deletes only files the fix added) instead of `BASE`, so the failure isolates the fixed behavior. This is an evidence-process gap, not a code defect, and the worker's report is not thereby false. Work down the ladder and stop at the first rung that succeeds:

1. **Recorded RED.** `report.md` holds the RED command and a failure excerpt that matches the missing behavior in the diff (for example, a failed assertion on the wrong value). A load, import or missing-export error is not RED: go to rung 2. Treat a valid excerpt as worker-attested evidence and record `Slice <ID>: ⚠️ resolved — <item> — attested RED: <command>; <excerpt>` in the progress ledger and, as a controller record, in `report.md`. Do not label it independently verified.
2. **Reconstructed RED.** Create a throwaway worktree outside the repository, detached at the reviewed tip (`git worktree add --detach <scratch path> <tip>`); it is never the workstream's isolation unit, so remove it (`git worktree remove --force`) before continuing, and again on resume if one is left over. In it, restore the slice's implementation files that existed at `BASE` (`git checkout BASE -- <paths>`) and delete the files the slice added; keep the tests. If the tests now fail to load (missing import or export), add minimal stubs for the missing symbols in the throwaway worktree only, so the failure is on assertions: an error or broken setup is not RED. The tests must fail for the intended missing behavior. Then run them at the tip for GREEN. Record `Slice <ID>: ⚠️ resolved — <item> — reconstructed RED (<tip sha>): <commands>; <failure excerpt>; GREEN at <tip sha>` in the progress ledger and append the same line to `report.md` as a controller record (reviewers receive the report, not the ledger). Treat a reviewer re-flag of the same ordering gap as resolved by this line; do not redispatch for it. This is fresh evidence labeled as such, not fabricated history. Leave the real branch untouched.
3. **Log the RED gap and proceed.** Only when neither rung applies (for example, edited existing tests entangled with the implementation, or a race or crash-window test that passes against the old code and cannot be made deterministic in one reconstruction attempt; do not keep redispatching evidence-only workers for it). Do not stop and do not ask the operator. Rung 2 must have been attempted. Proceed only if the slice is GREEN at the reviewed tip and the full suite passes; a red tip or suite is not DONE and goes back through the normal fix or verification route. A RED gap logged before review stays subject to that review: a reviewer finding showing a contract defect enters the fix loop as usual. Append one line to `<workspace>/red-gaps.md` (gitignored, next to `progress.md`; a separate container from `p2p3.md`, never mixed into it): `Slice <ID>: RED gap: <item> — rung 2 tried: <command> → <observed load, pass or nondeterministic output> — why it fails: <entangled test edits | nondeterministic race | cannot isolate> — worker-attested: <account, or none> — GREEN at <tip sha>` (`Final:` in place of `Slice <ID>:` during final review, and the ledger and report lines below follow suit). A line without the rung-2 attempt is not valid. De-duplicate by item before appending. Record `Slice <ID>: ⚠️ resolved — <item> — RED gap logged (red-gaps.md)` in the progress ledger and append the same RED gap line to `report.md` as a controller record (during final review, to `<workspace>/end-smoke-report.md`). Treat a reviewer re-flag of the same missing RED as resolved by this line; do not redispatch for it. This is an evidence-process gap, not a defect and not an independently verified RED: finish copies `red-gaps.md` into `<folder>/log.md` under a `RED gaps:` entry and tells the operator the count, separate from the P2/P3 count, so the operator can triage later (for example accept it or re-dispatch the slice).

Fix-round and preservation evidence follow the same ladder, with the exceptions that a refactor needs no RED and an unchanged-behavior test added against existing behavior is preservation evidence, never RED.

For `⚠️ Cannot verify from diff` items: requirements may live in unchanged code, depend on environment setup, or span multiple slices.

These items do not automatically fail the review, but you must resolve each one yourself before the slice can achieve **review clean**:
- Inspect the repository or worktree to check the requirement directly.
- If you verify the requirement is satisfied in existing code or architecture, record your resolution in the progress ledger:
  ```markdown
  Slice <ID>: ⚠️ resolved — <item> — <evidence>
  ```
  Recording this ensures your verification survives context compaction and session resume.
- If you confirm an actual gap, record it as an actionable spec gap and enter the fix loop (see [references/fix-loop.md](fix-loop.md)). Count it as open P0/P1 only when the reviewer assigns that severity; do not inflate the ledger count merely because the gap triggers the loop.
