# Resuming From an Existing Ledger

Part of `solopowers:workstream-driven-development`.

Conversation memory does not survive compaction. When a session ends mid-workstream (context compaction, session restart, crash, or user interruption), the durable progress ledger (`progress.md`) is the source of truth for slice state. The committed `<folder>/log.md` is the human/agent record (`Isolation:`, `Pre-flight:`, `Smoke:` lines, the `Final review:` outcome and the `P2/P3:` entry); it never overrides the ledger on slice state.

## Ledger Location and Workspace Identity

The ledger lives inside the per-workstream workspace directory. Run `scripts/wsd-workspace` by its absolute path, from the working tree you're executing in:
```bash
$(bash scripts/wsd-workspace <workspace-slug> WORKSTREAM_FILE)/progress.md
```
Or simply:
```bash
$(bash scripts/wsd-workspace WORKSTREAM_FILE)/progress.md
```
`WORKSTREAM_FILE` is always `<folder>/slices.md`; the helper derives the slug and date from the parent folder name.

### Ledger Header and Slug Disambiguation
- **Header format:** At create time, `wsd-workspace` writes `# Workstream: <path>` as the first line of `progress.md`.
- **Slug disambiguation:** If another workstream used the same slug, passing `WORKSTREAM_FILE` enables `wsd-workspace` to detect the mismatch and automatically disambiguate to a unique directory: `<slug>-<date>[-N]`.
- **Legacy headerless ledger adoption:** If an existing ledger has no header (e.g., created by an earlier version of solopowers), `wsd-workspace` emits a warning to stderr and adopts it. **Rule:** If an adopted legacy ledger already contains completed slices, confirm with the user before trusting them.

## Ledger State Lines

Per-slice entries in `progress.md` distinguish **state lines** (which define where execution stands) from **annotation lines** (`Ruling (user)`, `⚠️ resolved`, legacy `minor (deferred)`):

| Line | Written when |
|---|---|
| `Slice <ID>: fix round <R>/4 (<X> addressed, <Y> open — …; commits <a7>..<b7>)` | Written after each fix round re-review. "Open" always means open P0/P1; P2/P3 live in `p2p3.md`, never in the ledger. |
| `Slice <ID>: fix round 0/4 (<Y> open — initial review; commits <base7>..<head7>)` | Written when initial review requires a fix loop (NEEDS FIXES, ❌ spec compliance, or confirmed ⚠️ gap), before round 1 dispatch. Save actionable findings/gaps and uncertainties in `<workspace>/findings-<ID>.md`; `<Y>` counts open P0/P1 only and may be zero. |
| `Slice <ID>: escalated at cap — <Y> open` | Written when round 4 still has open findings. |
| `Slice <ID>: Ruling (user): <finding> — <decision>` | Annotation: written one per open finding once the user decides. |
| `Slice <ID>: ⚠️ resolved — <item> — <evidence>` | Annotation: written when the controller resolves a `⚠️ Cannot verify` item. |
| `Slice <ID>: complete (commits <base7>..<head7>, review clean[, <K> user rulings])` | Normal path: write only after a CLEAN review for the reviewed tip, credible Test Evidence for it, and all ⚠️ resolved. Cap path: named P0/P1 findings have user rulings that let the slice stand, with credible evidence and all ⚠️ resolved; CLEAN is not required. |

## Resume Dispatch Table

When resuming an interrupted session, locate the slice's **last state line** (skip `Ruling (user)`, `⚠️ resolved` and legacy `minor (deferred)` lines). Legacy smoke lines: a `review clean … awaiting smoke test` line counts as `complete` if `HEAD == <head7>`; if `HEAD != <head7>`, stop and ask the operator. A legacy `smoke test failed` line after it is not skipped: start fix loop round 1/4 with `FIX_BASE` = that `<head7>` and the reported failure as findings.

| Last state line | Action on resume |
|---|---|
| `complete` | Skip the slice (already DONE). Resume at the next slice. |
| `fix round <R>/4` (`1 <= R < 4`) | Require `HEAD == <b7>`. Before routing, resolve/correct any saved `⚠️ Cannot verify` or missing scoped verdict/Test Evidence and independently re-review the established exact range; if range/evidence cannot be established, stop and ask. Reconcile the saved findings/report with revised verdict and open count. Reuse a complete saved outcome only when both its base and tip exactly match the ledger's established `<a7>..<b7>` range and `HEAD == <b7>`; otherwise independently re-review that exact recorded range, or stop and ask if it cannot be established. Do not append a round during correction. For `0 open`, complete only with CLEAN, credible evidence, and resolved uncertainties. For `>0 open`, continue at round `<R+1>` only after the evidence gate. The R4 route is handled only by the cap rows below. |
| `fix round 0/4` (any open count) | This checkpoint saves an actionable fix-loop trigger; `<Y>` counts reviewer-graded P0/P1 only and may be zero. If `HEAD == <head7>`, resume round 1 from saved code gaps in `<workspace>/findings-<ID>.md`. Missing historical RED is not repairable by the fixer: preserve the issue as an evidence gap, attempt only evidence verifiable from the current tip, and escalate if pre-edit RED cannot be established. If trigger/report is missing or HEAD differs, stop and ask. |
| `fix round 4/4` (any open count), or `escalated at cap — <Y> open` with no rulings | Require `HEAD == <b7>` and apply the round-four evidence/range gate first. A round-four ledger range and existing findings file may establish a legacy findings-only checkpoint; do not require a separately saved verdict absent from legacy records. If range, findings, or evidence basis cannot be established, stop and ask. If corrected/reconciled outcome is CLEAN with `0 open`, complete through the normal clean route after credible evidence and uncertainty resolution; do not present an escalation. Otherwise re-present current escalation; **never dispatch round 5**. |
| `escalated at cap — <Y> open` followed by `Ruling (user)` lines | Require `HEAD == <b7>`. The round-four ledger range plus an existing findings file may establish legacy findings-only checkpoints; do not require a separately saved verdict that legacy records lack. If any evidence uncertainty was unresolved or corrected, independently re-review the established recorded round-four range before matching or acting on rulings, even when the saved outcome otherwise appears complete. Ensure credible Test Evidence for the reviewed revision; if the range, findings, or evidence basis cannot be established, stop and ask. Reuse a saved outcome only when its complete scoped range exactly matches the recorded round-four range and its tip matches `<b7>`. A legacy findings-only checkpoint is valid without a separately saved verdict: use its existing findings set with the exact ledger range/tip and evidence checks; missing verdict alone does not trigger re-review. Re-review if a modern outcome is incomplete, any outcome's range/tip mismatches, evidence uncertainty was corrected, or findings/evidence basis is otherwise incomplete. Reconcile current findings in the existing findings/report and preserve rulings. If revised/reconciled outcome is CLEAN with `0 open`, complete through the normal clean route after credible evidence and uncertainty resolution; do not apply stale rulings to absent findings. Otherwise match rulings to distinct current named findings; re-present unmatched findings and proceed only when every current finding has a ruling. If any ruling directs code changes, start a fresh 4-round series at `<b7>` with only those directed changes as findings; preserve accepted rulings. If no code changes are directed, completion requires credible evidence and resolved uncertainties; CLEAN is not required on the cap route. |
| No state line for this slice | Set `BASE` = previous slice's `complete` `<head7>` (for the first slice, the last setup commit: `git log -n1 --format=%H -G'^Pre-flight:' -- <folder>/log.md`, so Slice A's review excludes setup commits; if `log.md` has no `Pre-flight:` line, redo pre-flight first, see step 1a). If no commits exist past `BASE` (unstarted, or crashed before first commit), dispatch or resume the implementer from `BASE`. If commits exist past `BASE`: inspect the implementer report and any existing findings/review records. If a review or evidence correction was already dispatched, resume only from its recorded exact range and saved findings; if that range or reviewed tip cannot be established, stop and ask rather than rebuilding `BASE..HEAD`. If implementation reported `DONE` or `DONE_WITH_CONCERNS` (matching `SKILL.md`) and no review was dispatched, apply the same credible Test Evidence pre-review check as the live path before generating the initial slice review package. If evidence is incomplete, request correction before review; if interrupted after review, use existing findings records and exact range if available, otherwise stop and ask. Then run the initial slice review (`bash scripts/review-package BASE HEAD ...`). If the worker is not done, resume/re-dispatch the implementer. |
| `End smoke: failed … (at <h7>)` | If `HEAD == <h7>`, inspect the preceding `End smoke:` checkpoint. If this failure followed `End smoke: fix round <R>/4`, treat it as that round's post-review smoke rerun: resume at round `<R+1>` (`R < 4`) from `<workspace>/end-smoke-findings.md`, using a fresh implementer report; if `R == 4`, persist/re-present cap escalation and never start round 1. If there is no preceding fix-round checkpoint, this is the initial smoke failure and starts round 1/4. If the prior checkpoint/range cannot be established or `HEAD != <h7>`, stop and ask; do not infer a fresh budget.
| `End smoke: fix round <R>/4` where `1 <= R < 4` | Require `HEAD == <b7>`. First inspect the existing end-smoke report for a saved non-waivable Final verification blocker. If present, resolve it and run full Final verification before routing on the smoke ledger; do not re-enter smoke repair because of that blocker. After it passes, apply saved per-check rulings: skip explicitly accepted checks, rerun checks whose rulings directed fixes, and rerun other smoke checks only if code changed since their last successful run. Before any other routing, resolve/correct saved `⚠️ Cannot verify` or missing covering-test evidence and independently re-review the same range; if range/evidence cannot be established, stop and ask. Reconcile the complete revised scoped outcome and current open findings in the existing end-smoke findings/report; that same-range outcome controls routing only when exact range and matching tip are recorded, otherwise stop and re-review. This does not consume a round or change ledger syntax. For revised `0 open`, require the reconciled scoped verdict to be CLEAN, then re-run only smoke checks still open after applying any saved per-check rulings: skip explicitly accepted checks and rerun checks whose rulings directed fixes. Run Final verification in full. Write `passed` only when CLEAN, evidence is resolved, and every applicable check passes. If the smoke check fails, refresh its findings and append a new `End smoke: failed` line. If required Final verification fails, retain it as a non-waivable Final verification blocker in the existing report; do not append `End smoke: failed` or route it through the smoke fix/waiver loop. For revised `>0 open`, continue at round `<R+1>` using `<workspace>/end-smoke-report.md`. |
| `End smoke: fix round 4/4` (any open count), or `escalated at cap` with no rulings | Require `HEAD == <b7>`. First inspect the existing report for a saved non-waivable Final verification blocker. If present, resolve it and run full Final verification before routing on smoke state; after it passes, apply saved per-check rulings: skip explicitly accepted checks, rerun checks whose rulings directed fixes, and rerun other checks only if code changed since their last successful smoke run. A round-four ledger range and existing findings file may establish a legacy findings-only checkpoint; do not require a separately saved verdict absent from legacy records. Before routing, if any saved uncertainty or covering-test evidence gap is resolved/corrected, independently re-review the established exact round-four range; likewise re-review if a modern scoped outcome is incomplete or range/tip does not match. For a legacy findings-only checkpoint, absence of a separately saved verdict alone is not incompleteness: use the existing findings set with the exact ledger range/tip and evidence checks, and re-review only when uncertainty is corrected or findings/evidence basis is otherwise incomplete. Reconcile and persist any revised outcome and findings before routing. If range, findings, or evidence basis cannot be established, stop and ask. If revised outcome is CLEAN with `0 open`, require credible evidence and resolved uncertainties, then run only applicable smoke checks (skip explicitly waived checks; rerun directed-fix checks) and full Final verification; record passed only if all pass. Otherwise re-present current escalation; never dispatch round 5. |
| `End smoke: escalated at cap` followed by `Ruling (user)` lines | Require `HEAD == <b7>` from the preceding round-four line; otherwise stop and ask. A round-four ledger range and existing findings file may establish legacy findings-only checkpoints; do not require a separately saved verdict absent from legacy records. Reuse a saved outcome only when its complete scoped range exactly matches the recorded round-four range and its tip matches `<b7>`. If a modern outcome is absent/incomplete, its range or tip mismatches, or scoped evidence uncertainty was unresolved or corrected, independently re-review the established exact range before matching or acting on rulings; for legacy findings-only records, missing verdict alone does not trigger re-review. If the range cannot be established, stop and ask. Reconcile current findings in the existing findings/report and preserve rulings. If range, findings, or evidence basis cannot be established, stop and ask. Match rulings to distinct current named findings and separate rulings that accept a check from those directing code changes; re-present unmatched findings and wait until every current finding has a ruling. If any ruling directs a code change, start fresh round 1/4 at `<b7>` with only currently directed findings, preserving accepted rulings; after that series is review-clean, rerun only the checks attached to directed fixes. Otherwise, if revised/reconciled code-review outcome is CLEAN with `0 open`, keep any separate cap smoke failure unresolved unless it has an explicit acceptance ruling. Do not let CLEAN code review erase or rerun an unruled cap failure. Skip explicitly accepted checks; run full Final verification after evidence is resolved, and record passed only if CLEAN and all applicable checks pass. If no code changes are directed, do not rerun the waived check; this waiver applies only to an explicit user ruling accepting that named smoke failure. Run full Final verification only after evidence is resolved. If it passes, write `End smoke: passed (rulings accepted)`. If Final verification fails, keep that failure as a required, non-waivable Final verification blocker in the existing report; do not append `End smoke: failed` or route it through the smoke fix/waiver loop. On restart, resolve the Final verification blocker and rerun Final verification before recording smoke passed.

### End smoke line

After the last slice, `progress.md` carries `End smoke: pending|passed|skipped|failed|fix round|escalated` ([end-smoke.md](end-smoke.md)). On resume with every slice `complete`: no line or `pending` means rerun Final verification, then the end-smoke step; `passed`/`skipped` (including `passed (rulings accepted)`) means go to final review (`passed` is only written after full Final verification passed; a Final verification failure is a non-waivable blocker, not an `End smoke: failed` condition). If `progress.md` has `End: final review fix wave (commits <a7>..<b7>)` and the log has no `Final review: clean` marker, run only Final verification and one re-review of that wave (no second fix wave; unresolved P0/P1 go to the operator). After the final review, the committed `Final review: clean (at <h7>)` line in `log.md` marks the workstream finished (step 0 handles it before any ledger access; the ledger is deleted at cleanup). The ledger is append-only; the last `End smoke:` state line wins (ignore `Ruling (user)` lines); `failed`, `fix round` and `escalated` lines resume per the `End smoke:` rows above (the table is otherwise per slice), never by rerunning the whole smoke.

## Step-by-Step Resume Procedure

0. **Locate the isolation unit BEFORE any `wsd-workspace` call** (it silently creates an empty ledger in whatever checkout you are in). After a restart you may be in the main checkout (worktree mode) or on the default branch after `git switch main` (branch mode).
   - Derive `<slug>`: the workstream folder name minus its leading `YYYY-MM-DD-`. Run `git worktree list --porcelain` and `git branch --list 'ws/<slug>'`. Match worktrees by the exact line `branch refs/heads/ws/<slug>` (never a prefix match: `foo` vs `foo-bar`); if none matches, for a worktree found by other means (its tree contains `<folder>/log.md`), its `Isolation:` line records the branch name (a branch that could not be renamed to `ws/<slug>`); the log is read from that unit's tree, so this lookup does not work from the main checkout; the fallback below covers that case. If several candidate worktrees or branches match, stop and ask the operator.
   - **Worktree mode:** if a worktree on `ws/<slug>` exists (or any worktree whose tree contains `<folder>/log.md` with an `Isolation:` line anywhere in it), `cd` into that worktree directory. Every later step (`wsd-workspace`, `slice-brief`, ledger, `log.md`, commits) runs there.
   - **Branch mode:** if branch `ws/<slug>` exists and you are not on it, first validate with `git show ws/<slug>:<folder>/log.md` that it contains an `Isolation:` line (if not, stop and ask the operator), then run `git switch ws/<slug>` only when the working tree is clean; otherwise stop and ask the operator.
   - Read the mode from `<folder>/log.md` IN THE UNIT. **Stop and ask the operator** (never dispatch an implementer on the default branch, never run `wsd-workspace` outside the unit) if: the unit's `log.md` has no `Isolation:` line anywhere; no unit can be found but a ledger or log shows work was done (except a merged workstream: on the default branch, if `git show HEAD:<folder>/log.md` has a `Final review: clean` marker, report "finished and merged" per the Finished check instead of asking); or you are on the default branch while a `ws/<slug>` branch exists and cannot be switched to.
   - **Finished check (still before any `wsd-workspace` call or step 1):** look for a `Final review: clean (at <h7>)` line in BOTH `git show HEAD:<folder>/log.md` and the working-tree `<folder>/log.md`.
     - Marker in `HEAD`: finished. Ignore unrelated `log.md` dirtiness (do not commit it).
     - Marker only in the working tree (uncommitted): the outcome commit did not happen. Commit `<folder>/log.md` AND `<folder>/brief.md` together by explicit path (`Status: Done` is part of it), then treat as finished.
     - No marker anywhere: not finished; continue the normal resume (Finish step 2 must check `log.md` first so it does not append duplicate `Smoke:`/`P2/P3:`/`Final review:` lines).
     - When finished: do NOT run `wsd-workspace`, dispatch anything, or rerun reviews. Find the marker commit `MC=$(git log -n1 --format=%H -G'^Final review: clean' -- <folder>/log.md)` and compare `HEAD` with `MC` (not `<h7>`): if `HEAD` has commits past `MC`, tell the operator and ask. If `HEAD == MC`, offer `solopowers:finishing-a-development-branch`, or, if a PR/keep outcome was already chosen, just report the state. After a local merge the unit is gone: on the default branch with no `ws/<slug>` unit, if `git show HEAD:<folder>/log.md` shows `Final review: clean`, report "finished and merged" instead of restarting.
   - Only if NO `ws/<slug>` branch or worktree exists AND no `Isolation:` line exists anywhere is this a first run, not a resume: go through the normal isolation choice ([references/isolation.md](isolation.md)).
1. From inside the unit, run `bash scripts/wsd-workspace <folder>/slices.md` to identify the resolved workspace directory.
1a. **Pre-flight check.** If `log.md` in the unit has an `Isolation:` line but no `Pre-flight:` line, setup was interrupted (no fallback to the `Isolation:` commit; `BASE` is the last `Pre-flight:` commit): before dispatching anything, redo the pre-flight scan inside the unit ([references/preflight.md](preflight.md)), apply agreed edits, and append and commit the `Pre-flight:` line. Otherwise skip pre-flight.
2. Read `<workspace>/progress.md` for slice state, and confirm the isolation mode from `log.md` in the unit (the first `Isolation: <branch|worktree> — branch <name>` line anywhere in it). Do not ask the operator to choose isolation again; if the mode in `log.md` does not match the current checkout, stop and ask.
3. If the ledger is legacy headerless and marks slices complete, confirm with the user: "Adopted existing ledger for <workstream>. Slices [X, Y] are marked complete in the ledger. Proceed with Slice [Z]?"
4. Inspect the last state line for the first incomplete slice according to the Resume Dispatch Table above.
5. Take the corresponding action from the table, carrying forward context from the preceding completed slice.
