# Resuming From an Existing Ledger

Part of `solopowers:workstream-driven-development`.

Conversation memory does not survive compaction. When a session ends mid-workstream (context compaction, session restart, crash, or user interruption), the durable progress ledger (`progress.md`) is the source of truth for slice state. The committed `<folder>/log.md` is the human/agent record (`Isolation:`, `Pre-flight:`, `Smoke:` lines, the `Final review:` outcome and the `P2/P3:` entry); it never overrides the ledger on slice state.

## Ledger Location and Workspace Identity

The ledger lives inside the per-workstream workspace directory. Run `scripts/wsd-workspace` by its absolute path, from the working tree you're executing in:
```bash
$(bash scripts/wsd-workspace <workspace-slug> WORKSTREAM_FILE)/progress.md
```
Or simply:
```bash
$(bash scripts/wsd-workspace WORKSTREAM_FILE)/progress.md
```
`WORKSTREAM_FILE` is always `<folder>/slices.md`; the helper derives the slug and date from the parent folder name.

### Ledger Header and Slug Disambiguation
- **Header format:** At create time, `wsd-workspace` writes `# Workstream: <path>` as the first line of `progress.md`.
- **Slug disambiguation:** If another workstream used the same slug, passing `WORKSTREAM_FILE` enables `wsd-workspace` to detect the mismatch and automatically disambiguate to a unique directory: `<slug>-<date>[-N]`.
- **Legacy headerless ledger adoption:** If an existing ledger has no header (e.g., created by an earlier version of solopowers), `wsd-workspace` emits a warning to stderr and adopts it. **Rule:** If an adopted legacy ledger already contains completed slices, confirm with the user before trusting them.

## Ledger State Lines

Per-slice entries in `progress.md` distinguish **state lines** (which define where execution stands) from **annotation lines** (`Ruling (user)`, `⚠️ resolved`, legacy `minor (deferred)`):

| Line | Written when |
|---|---|
| `Slice <ID>: fix round <R>/4 (<X> addressed, <Y> open — …; commits <a7>..<b7>)` | Written after each fix round re-review. "Open" always means open P0/P1; P2/P3 live in `p2p3.md`, never in the ledger. |
| `Slice <ID>: fix round 0/4 (<Y> open — initial review; commits <base7>..<head7>)` | Written when initial review requires a fix loop (NEEDS FIXES, ❌ spec compliance, or confirmed ⚠️ gap), before round 1 dispatch. Save actionable findings/gaps and uncertainties in `<workspace>/findings-<ID>.md`; `<Y>` counts open P0/P1 only and may be zero. |
| `Slice <ID>: escalated at cap — <Y> open` | Written when round 4 still has open findings. |
| `Slice <ID>: Ruling (user): <finding> — <decision>` | Annotation: written one per open finding once the user decides. |
| `Slice <ID>: ⚠️ resolved — <item> — <evidence>` | Annotation: written when the controller resolves a `⚠️ Cannot verify` item. |
| `Slice <ID>: complete (commits <base7>..<head7>, review clean[, <K> user rulings])` | Normal path: write only after a CLEAN review for the reviewed tip, credible Test Evidence for it, and all ⚠️ resolved. Cap path: named P0/P1 findings have user rulings that let the slice stand, with credible evidence and all ⚠️ resolved; CLEAN is not required. |

## Resume Dispatch Table

When resuming an interrupted session, first inspect `<workspace>/end-smoke-report.md` for a final-review fix-wave continuation before any generic blocker or pending-smoke route. Establish the exact candidate range and durable dispatch state. If a completed outcome exists, apply its verdict before blocker routing: only applicable CLEAN continues; any unresolved findings go to the operator; uncertain coverage stops. Then inspect the active Final verification blocker and establish the accepted repair candidate and passing current Final verification as required by [Final Verification Blocker](verification-blocker.md). This does not mark the blocker `RESOLVED`; outstanding smoke obligations remain for after the re-review. Only then authorize a fresh dispatch for that exact candidate/range when durable state establishes it was not dispatched. Recover an existing dispatch without redispatch; reuse a completed outcome. Missing or ambiguous legacy dispatch state or coverage means stop and ask. Persist known-undispatched continuation before or with the wave checkpoint where practical; separate file writes are not atomic. After the re-review has been used, preserve saved smoke failure/cap evidence but stop for operator direction before any code-changing dispatch; only authorized non-code checks/reconciliation may continue. Then inspect for an active non-waivable Final verification blocker before selecting any resume-table row or applying its `HEAD` guard. If blocker is `ACTIVE`, follow [Final Verification Blocker](verification-blocker.md) before selecting a smoke row. If the blocker records `INITIAL SMOKE PENDING`, first inspect the durable smoke ledger/progress. Before normal initial-smoke dispatch, select the latest applicable smoke checkpoint across the append-only ledger/progress and `log.md`. If a newer failure, fix-round, or escalation checkpoint exists than a passed/skipped outcome, resume that newer checkpoint and do not reconcile the older success or resolve the blocker. Only when the latest checkpoint is passed or skipped may you validate `HEAD` against its recorded passing revision or a newer valid smoke checkpoint, establish that the outcome remains applicable, reconcile current passing Final verification, add only a missing paired record, and mark the blocker `RESOLVED`. If ordering, revision applicability, or current checkpoint is uncertain, stop and ask. Never replay completed checks or duplicate log entries. Otherwise resume that exact row and never replay completed checks. If none exists, require `HEAD` at the recorded passing revision and current full Final verification before entering the normal initial-smoke workflow. If `HEAD` differs without a valid smoke checkpoint, stop and ask; this is not revalidation. If verification revalidation is pending, first validate `HEAD` against the applicable repair tip, or the pending record’s passing revision when no repair tip exists, unless a newer valid smoke checkpoint supersedes it; then reconcile durable per-check results with the latest smoke checkpoint. Reconcile all recorded failures together using the shared procedure in [Final Verification Blocker](verification-blocker.md): materialize each check as a distinct actionable finding, but append one failure/escalation ledger transition for the group, preserving the originating round/budget; never emit consecutive per-check failure lines that reset the route. Reuse a transition only when its exact association with that group is established; if append status or association is ambiguous, stop and ask rather than duplicate it. Do not rerun failed checks during reconciliation. Preserve history and rulings. The newest valid fix-round checkpoint governs resumption of an already-dispatched fix series, whether CLEAN or not; it does not authorize smoke reruns. Only an independently review-clean checkpoint authorizes its outstanding smoke reruns. Resume the recorded series without redispatching or resetting budget. Apply its saved verdict before routing: applicable CLEAN continues; unresolved findings escalate; uncertain coverage stops. Do not redispatch or start a second wave. Reuse successful results valid at this revision and run only outstanding checks. After reconciliation, only the current applicable `End smoke: escalated at cap` state with a current unruled finding takes precedence over further revalidation, including failures outside the pending check set: re-present those unresolved findings and wait; do not run smoke checks until rulings are complete. A superseded historical escalation does not block a newer durable fix-round series; resume that authorized series and preserve the older ruling/history. A recorded failure resumes the failure/escalation route without rerunning that check; a cap ruling directing code changes hands off to the authorized fix series while retaining pending revalidation. Otherwise perform only outstanding authorized revalidation. Same-tip recovery needs no repair review; a committed repair resumes from its recorded base/tip and scoped-review outcome. Mark the blocker resolved only after all required checks are passed/disposed, full Final verification passes, and the corresponding smoke outcome is durably recorded; retain its history. If range or active/resolved status is ambiguous, stop and ask. The saved smoke checkpoint remains authoritative for budget and rulings, but not for the repair tip. Then locate the slice's **last state line** (skip `Ruling (user)`, `⚠️ resolved` and legacy `minor (deferred)` lines). Legacy smoke lines: a `review clean … awaiting smoke test` line counts as `complete` if `HEAD == <head7>`; if `HEAD != <head7>`, stop and ask the operator. A legacy `smoke test failed` line after it is not skipped: start fix loop round 1/4 with `FIX_BASE` = that `<head7>` and the reported failure as findings.

### End smoke line

After the last slice, `progress.md` carries `End smoke: pending|passed|skipped|failed|fix round|escalated` ([end-smoke.md](end-smoke.md)). On resume with every slice `complete`, first inspect any saved final-review fix-wave continuation in `<workspace>/end-smoke-report.md` before generic smoke revision reconciliation or routing any pending smoke failure/fix/escalation. Its recorded wave/re-review range validates the continuation tip even when it is newer than the last smoke checkpoint; before finish, assess each saved smoke result's applicability from its own revision through the current candidate tip, including all fix-wave and verification-repair changes, and revalidate every invalidated or outstanding check. For this continuation, use the authoritative sequence above and [Final Verification Blocker](verification-blocker.md): apply a saved outcome's verdict before blocker routing, and require current Final verification only before a fresh dispatch. Do not resolve the blocker merely to dispatch; outstanding smoke obligations remain finish gates. Missing or ambiguous legacy dispatch state or coverage means stop and ask. A smoke failure requiring code changes after that review stops for operator direction; do not dispatch another fix series. Then: no line or `pending` means rerun Final verification, then the end-smoke step; `passed`/`skipped` (including `passed (rulings accepted)`) first requires generic paired-record reconciliation: inspect both `progress.md` and `log.md`, validate `HEAD` and evidence applicability against the recorded smoke revision or a newer valid smoke checkpoint, and write only the missing counterpart. If applicability cannot be established, stop and ask; do not replay completed checks. Then go to final review (`passed` is only written after full Final verification passed; a Final verification failure is a non-waivable blocker, not an `End smoke: failed` condition). If `progress.md` has `End: final review fix wave (commits <a7>..<b7>)` and the log has no `Final review: clean` marker, follow the exact-range and durable-dispatch checks above and [Final Verification Blocker](verification-blocker.md); never authorize a second fix wave. For any recorded final-review fix-wave continuation, reconcile its saved continuation in `<workspace>/end-smoke-report.md` before the generic fix-wave route, whether or not `HEAD` moved and whether or not a verification blocker is active: if the one re-review was dispatched or completed, never dispatch it again; resume from its saved range/outcome. A report created solely for this continuation is not an `ACTIVE` blocker. For legacy records lacking dispatch state, or if state or coverage is uncertain, stop and ask rather than redispatch. If verification-blocker recovery records a later commit/tip after `<b7>`, validate the accepted repair tip and current full Final verification, and preserve outstanding smoke obligations without adding ledger markers. Follow the authoritative dispatch-state route above: launch the combined original-wave-base..current-`HEAD` review only when durably known undispatched; otherwise recover or reuse the recorded review without redispatch, and stop for operator direction if its coverage does not include the current candidate. Never dispatch an extra review or finish on a stale range. After the final review, the committed `Final review: clean (at <h7>)` line in `log.md` marks the workstream finished (step 0 handles it before any ledger access; the ledger is deleted at cleanup). The ledger is append-only; the last `End smoke:` state line wins (ignore `Ruling (user)` lines); `failed`, `fix round` and `escalated` lines resume per the `End smoke:` rows above (the table is otherwise per slice), never by rerunning the whole smoke.

## Step-by-Step Resume Procedure

0. **Locate the isolation unit BEFORE any `wsd-workspace` call** (it silently creates an empty ledger in whatever checkout you are in). After a restart you may be in the main checkout (worktree mode) or on the default branch after `git switch main` (branch mode).
   - Derive `<slug>`: the workstream folder name minus its leading `YYYY-MM-DD-`. Run `git worktree list --porcelain` and `git branch --list 'ws/<slug>'`. Match worktrees by the exact line `branch refs/heads/ws/<slug>` (never a prefix match: `foo` vs `foo-bar`); if none matches, for a worktree found by other means (its tree contains `<folder>/log.md`), its `Isolation:` line records the branch name (a branch that could not be renamed to `ws/<slug>`); the log is read from that unit's tree, so this lookup does not work from the main checkout; the fallback below covers that case. If several candidate worktrees or branches match, stop and ask the operator.
   - **Worktree mode:** if a worktree on `ws/<slug>` exists (or any worktree whose tree contains `<folder>/log.md` with an `Isolation:` line anywhere in it), `cd` into that worktree directory. Every later step (`wsd-workspace`, `slice-brief`, ledger, `log.md`, commits) runs there.
   - **Branch mode:** if branch `ws/<slug>` exists and you are not on it, first validate with `git show ws/<slug>:<folder>/log.md` that it contains an `Isolation:` line (if not, stop and ask the operator), then run `git switch ws/<slug>` only when the working tree is clean; otherwise stop and ask the operator.
   - Read the mode from `<folder>/log.md` IN THE UNIT. **Stop and ask the operator** (never dispatch an implementer on the default branch, never run `wsd-workspace` outside the unit) if: the unit's `log.md` has no `Isolation:` line anywhere; no unit can be found but a ledger or log shows work was done (except a merged workstream: on the default branch, if `git show HEAD:<folder>/log.md` has a `Final review: clean` marker, report "finished and merged" per the Finished check instead of asking); or you are on the default branch while a `ws/<slug>` branch exists and cannot be switched to.
   - **Finished check (still before any `wsd-workspace` call or step 1):** look for a `Final review: clean (at <h7>)` line in BOTH `git show HEAD:<folder>/log.md` and the working-tree `<folder>/log.md`.
     - Marker in `HEAD`: finished. Ignore unrelated `log.md` dirtiness (do not commit it).
     - Marker only in the working tree (uncommitted): the outcome commit did not happen. Commit `<folder>/log.md` AND `<folder>/brief.md` together by explicit path (`Status: Done` is part of it), then treat as finished.
     - No marker anywhere: not finished; continue the normal resume (Finish step 2 must check `log.md` first so it does not append duplicate `Smoke:`/`P2/P3:`/`Final review:` lines).
     - When finished: do NOT run `wsd-workspace`, dispatch anything, or rerun reviews. Find the marker commit `MC=$(git log -n1 --format=%H -G'^Final review: clean' -- <folder>/log.md)` and compare `HEAD` with `MC` (not `<h7>`): if `HEAD` has commits past `MC`, tell the operator and ask. If `HEAD == MC`, offer `solopowers:finishing-a-development-branch`, or, if a PR/keep outcome was already chosen, just report the state. After a local merge the unit is gone: on the default branch with no `ws/<slug>` unit, if `git show HEAD:<folder>/log.md` shows `Final review: clean`, report "finished and merged" instead of restarting.
   - Only if NO `ws/<slug>` branch or worktree exists AND no `Isolation:` line exists anywhere is this a first run, not a resume: go through the normal isolation choice ([references/isolation.md](isolation.md)).
1. From inside the unit, run `bash scripts/wsd-workspace <folder>/slices.md` to identify the resolved workspace directory.
1a. **Pre-flight check.** If `log.md` in the unit has an `Isolation:` line but no `Pre-flight:` line, setup was interrupted (no fallback to the `Isolation:` commit; `BASE` is the last `Pre-flight:` commit): before dispatching anything, redo the pre-flight scan inside the unit ([references/preflight.md](preflight.md)), apply agreed edits, and append and commit the `Pre-flight:` line.
