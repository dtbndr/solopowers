# Resuming From an Existing Ledger

Part of `solopowers:workstream-driven-development`.

Conversation memory does not survive compaction. When a session ends mid-workstream (context compaction, session restart, crash, or user interruption), the durable progress ledger (`progress.md`) is the source of truth for slice state. The committed `<folder>/log.md` is the human/agent record (`Isolation:`, `Pre-flight:`, `Smoke:` lines, the `Final review:` outcome and the `P2/P3:` entry); it never overrides the ledger on slice state.

## Ledger Location and Workspace Identity

The ledger lives inside the per-workstream workspace directory. Run `scripts/wsd-workspace` by its absolute path, from the working tree you're executing in:
```bash
$(bash scripts/wsd-workspace <workspace-slug> WORKSTREAM_FILE)/progress.md
```
Or simply:
```bash
$(bash scripts/wsd-workspace WORKSTREAM_FILE)/progress.md
```
`WORKSTREAM_FILE` is always `<folder>/slices.md`; the helper derives the slug and date from the parent folder name.

### Ledger Header and Slug Disambiguation
- **Header format:** At create time, `wsd-workspace` writes `# Workstream: <path>` as the first line of `progress.md`.
- **Slug disambiguation:** If another workstream used the same slug, passing `WORKSTREAM_FILE` enables `wsd-workspace` to detect the mismatch and automatically disambiguate to a unique directory: `<slug>-<date>[-N]`.
- **Legacy headerless ledger adoption:** If an existing ledger has no header (e.g., created by an earlier version of solopowers), `wsd-workspace` emits a warning to stderr and adopts it. **Rule:** If an adopted legacy ledger already contains completed slices, confirm with the user before trusting them.

## Ledger State Lines

Per-slice entries in `progress.md` distinguish **state lines** (which define where execution stands) from **annotation lines** (`Ruling (user)`, `⚠️ resolved`, legacy `minor (deferred)`):

| Line | Written when |
|---|---|
| `Slice <ID>: fix round <R>/4 (<X> addressed, <Y> open — …; commits <a7>..<b7>)` | Written after each fix round re-review. "Open" always means open P0/P1; P2/P3 live in `p2p3.md`, never in the ledger. |
| `Slice <ID>: fix round 0/4 (<Y> open — initial review; commits <base7>..<head7>)` | Written when initial review requires a fix loop (NEEDS FIXES, ❌ spec compliance, or confirmed ⚠️ gap), before round 1 dispatch. Save actionable findings/gaps and uncertainties in `<workspace>/findings-<ID>.md`; `<Y>` counts open P0/P1 only and may be zero. |
| `Slice <ID>: escalated at cap — <Y> open` | Written when round 4 still has open findings. |
| `Slice <ID>: Ruling (user): <finding> — <decision>` | Annotation: written one per open finding once the user decides. |
| `Slice <ID>: ⚠️ resolved — <item> — <evidence>` (`Final:` in place of `Slice <ID>:` during final review) | Annotation: written when the controller resolves a `⚠️ Cannot verify` item. |
| `Slice <ID>: complete (commits <base7>..<head7>, review clean[, <K> user rulings])` | Normal path: write only after a CLEAN review for the reviewed tip, credible Test Evidence for it, and all ⚠️ resolved. Cap path: named P0/P1 findings have user rulings that let the slice stand, with credible evidence and all ⚠️ resolved; CLEAN is not required. |

## Resume Dispatch Table

Before any resume route below runs or requests a smoke check, apply [end-smoke.md](end-smoke.md)'s authorization rule: an external or side-effecting action requires explicit operator OK in the current session for that specific action. A prior session's authorization or a ruling that directs code fixes does not authorize the smoke action; if authorization is absent, request operator action and do not perform or rerun the check.

When resuming an interrupted session, first inspect `<workspace>/end-smoke-report.md` for a final-review fix-wave continuation before any generic blocker or pending-smoke route. Establish the exact candidate range and durable dispatch state. If a completed outcome exists, apply its verdict before blocker routing: only applicable CLEAN continues; any unresolved findings go to the operator; uncertain coverage stops. Then inspect the active Final verification blocker and establish the accepted repair candidate and passing current Final verification as required by [Final Verification Blocker](verification-blocker.md). This does not mark the blocker `RESOLVED`; outstanding smoke obligations remain for after the re-review. Only then authorize a fresh dispatch for that exact candidate/range when an existing durable record establishes it was not dispatched. Recover an existing dispatch without redispatch; reuse a completed outcome. Resume by reconciling the existing continuation record, not by creating or restoring known-undispatched intent. If that record is absent, incomplete, or ambiguous, or exact-range evidence cannot establish its association with the checkpoint, stop and ask. A pending record is neither passing verification nor proof of dispatch. Separate file writes are not atomic: reconcile only when exact-range evidence makes the association unambiguous; otherwise stop. After the re-review has been used, preserve saved smoke failure/cap evidence but stop for operator direction before any code-changing dispatch; only authorized non-code checks/reconciliation may continue. After final-review continuation precedence, inspect the latest applicable full Final verification attempt before acting on pending smoke state or selecting a smoke row. Use this shared cap-write sequence for restart and newly observed round-four failures before further work: determine from durable findings/report evidence whether a concurrent round-four smoke failure group exists, including its exact revision and originating round. If records indicate such a group may exist but membership, revision, or round cannot be established, stop and ask; do not infer or write a cap transition. If the group is established, durably record any applicable, unsuperseded, unrecovered Final verification failure with its command, result, and exact failing revision before reconciling the cap transition as bookkeeping: append once only when absence is proven, otherwise reuse only a transition proven to cover that exact group and revision; stop if coverage is uncertain. Do not dispatch smoke or hand off rulings. Do not require or infer a cap transition for verification-only failures or legacy smoke-only records. Then, if the latest applicable verification attempt establishes an unrecovered failure, complete any missing `ACTIVE` marker and enter [Final Verification Blocker](verification-blocker.md) recovery. An applicable full pass with smoke revalidation pending advances to that pending route; it does not reactivate the historical failure or resolve the blocker before the smoke outcome is durable. Stop if attempt applicability or ordering is ambiguous. Do not infer failure from a cap marker or absent pass. Then inspect for an active non-waivable Final verification blocker before selecting any resume-table row or applying its `HEAD` guard. If blocker is `ACTIVE`, follow [Final Verification Blocker](verification-blocker.md) before selecting a smoke row. If the blocker records `INITIAL SMOKE PENDING`, first inspect the durable smoke ledger/progress. Before normal initial-smoke dispatch, select the latest applicable smoke checkpoint across the append-only ledger/progress and `log.md`. If a newer failure, fix-round, or escalation checkpoint exists than a passed/skipped outcome, resume that newer checkpoint and do not reconcile the older success or resolve the blocker. Only when the latest checkpoint is passed or skipped may you validate `HEAD` against its recorded passing revision or a newer valid smoke checkpoint, establish that the outcome remains applicable, reconcile current passing Final verification, add only a missing paired record, and mark the blocker `RESOLVED`. If ordering, revision applicability, or current checkpoint is uncertain, stop and ask. Never replay completed checks or duplicate log entries. Otherwise resume that exact row and never replay completed checks. If none exists, require `HEAD` at the recorded passing revision and current full Final verification before entering the normal initial-smoke workflow. If `HEAD` differs without a valid smoke checkpoint, stop and ask; this is not revalidation. If verification revalidation is pending, first validate `HEAD` against the applicable repair tip, or the pending record’s passing revision when no repair tip exists, unless a newer valid smoke checkpoint supersedes it; then reconcile durable per-check results with the latest smoke checkpoint. Reconcile all recorded failures together using the shared procedure in [Final Verification Blocker](verification-blocker.md): materialize each check as a distinct actionable finding, but append one failure/escalation ledger transition for the group, preserving the originating round/budget; never emit consecutive per-check failure lines that reset the route. Reuse a transition only when its exact association with that group is established; if append status or association is ambiguous, stop and ask rather than duplicate it. Do not rerun failed checks during reconciliation. Preserve history and rulings. The newest valid fix-round checkpoint governs resumption of an already-dispatched fix series, whether CLEAN or not; it does not authorize smoke reruns. Only an independently review-clean checkpoint authorizes its outstanding smoke reruns. Resume the recorded series without redispatching or resetting budget. For actionable open findings after round R below cap, record round R+1 as the pending route, not a dispatch instruction. Before dispatch, satisfy the applicable saved-evidence and verdict gates above, and complete any verification-blocker recovery that takes precedence. Use the cap rows for round-four findings. Stop if range or coverage is uncertain. Do not redispatch the existing series. Reuse successful results valid at this revision and run only outstanding checks. After reconciliation, only the current applicable `End smoke: escalated at cap` state with a current unruled finding takes precedence over further revalidation, including failures outside the pending check set: re-present those unresolved findings and wait; do not run smoke checks until rulings are complete. A superseded historical escalation does not block a newer durable fix-round series; resume that authorized series and preserve the older ruling/history. A recorded failure resumes the failure/escalation route without rerunning that check; a cap ruling directing code changes hands off to the authorized fix series while retaining pending revalidation. Otherwise perform only outstanding authorized revalidation. Same-tip recovery needs no repair review; a committed repair resumes from its recorded base/tip and scoped-review outcome. Mark the blocker resolved only after all required checks are passed/disposed, full Final verification passes, and the corresponding smoke outcome is durably recorded; retain its history. If range or active/resolved status is ambiguous, stop and ask. The saved smoke checkpoint remains authoritative for budget and rulings, but not for the repair tip. Then locate the slice's **last state line** (skip `Ruling (user)`, `⚠️ resolved` and legacy `minor (deferred)` lines). ### End smoke line

After the last slice, `progress.md` carries `End smoke: pending|passed|skipped|failed|fix round|escalated` ([end-smoke.md](end-smoke.md)). On resume with every slice `complete`, first inspect any saved final-review fix-wave continuation in `<workspace>/end-smoke-report.md` before generic smoke revision reconciliation or routing any pending smoke failure/fix/escalation. Its recorded wave/re-review range validates the continuation tip even when it is newer than the last smoke checkpoint; before finish, assess each saved smoke result's applicability from its own revision through the current candidate tip, including all fix-wave and verification-repair changes, and revalidate every invalidated or outstanding check. For this continuation, use the authoritative sequence above and [Final Verification Blocker](verification-blocker.md): apply a saved outcome's verdict before blocker routing, and require current Final verification only before a fresh dispatch. Do not resolve the blocker merely to dispatch; outstanding smoke obligations remain finish gates. Missing or ambiguous legacy dispatch state or coverage means stop and ask. A smoke failure requiring code changes after that review stops for operator direction; do not dispatch another fix series. Then: no line or `pending` means first inspect `log.md` for a possible outcome belonging to the current applicable smoke checkpoint, after the blocker, final-review continuation, and newer-checkpoint routes above. If a log-only outcome is established, verify its revision, evidence applicability, and marker type. Do not replay valid smoke checks or infer ordinary, mixed-ruling, or acceptance-only marker type from a lone `Smoke: passed` line. If candidate outcome or marker type is ambiguous, stop and ask; do not repeat checks, especially side-effecting checks that lack authorization. If no applicable log-only outcome exists, keep the current route of rerunning Final verification and then continuing the end-smoke step. Reuse an established pass only if it remains applicable to the current revision and verification conditions; otherwise run full Final verification without replaying completed smoke checks. For `passed (rulings accepted)` or an ordinary `passed` outcome with applicable mixed cap rulings, reconstruct a missing log one-liner from the applicable named rulings so waived checks are identified and never implied to have passed; if the marker type or ruling applicability cannot be established, stop and ask rather than infer it. Then go to final review (`passed` is only written after full Final verification passed; a Final verification failure is a non-waivable blocker, not an `End smoke: failed` condition). If several candidate worktrees or branches match, stop and ask the operator.

   - **Branch mode:** if branch `ws/<slug>` exists and you are not on it, first validate with `git show ws/<slug>:<folder>/log.md` that it contains an `Isolation:` line (if not, stop and ask the operator), then run `git switch ws/<slug>` only when the working tree is clean; otherwise stop and ask the operator.
